# 實測規劃（階段一）

目標：這週內帶上公車，收集第一批台北公車的加速度資料，並回答三個問題：

1. **手機放法差多少？** 同一趟、同一時間，支架、座椅、手持三支手機與硬體感測盒的讀數差異。
2. **偵測準不準？** 自動偵測的急煞與「人工按鈕標記」、硬體盒的一致率（對照 Ma 2018：完全一致 63.6%）。
3. **門檻合不合理？** 台北公車的加速度、加加速度（jerk）分布，P95 落在哪裡，預設門檻要不要調。

## 器材

| 項目 | 數量 | 備註 |
|---|---|---|
| 手機 | 3 支 | 至少一支 iPhone、一支 Android；開「順順行」網頁，先加到主畫面 |
| 手機支架 | 1 | 夾在椅背扶手或立桿上；**要夾緊**，晃動會被判成不穩定 |
| 硬體感測盒 | 1 | ESP32 + IMU，用束帶固定在座椅骨架（見 `hardware/README.md`） |
| 行動電源＋短線 | 3 | 螢幕全程常亮，一小時約耗 15 至 25% 電量（待實測） |
| 紀錄表 | 1 | 紙本或共用試算表，欄位見下方 |

## 路線與時段

先搭**中山幹線**（班次多、路線長、有幹線公車的代表性）。

| 趟次 | 時段 | 座位 | 目的 |
|---|---|---|---|
| 1 | 平日離峰（10:00 至 16:00）去程 | 中段 | 熟悉流程、確認資料品質 |
| 2 | 平日離峰回程 | 中段 | 同上，雙向比較 |
| 3 | 平日離峰 | **後排** | 後排車身震動較大（Ma 2018 後排異常率 42% vs 前排 11%） |
| 4 | 平日離峰 | **前排** | 與第 3 趟對照 |
| 5、6 | 平日尖峰（07:00 至 09:00 或 17:00 至 19:00） | 中段 | 尖峰是否較多急煞（班表壓力） |

每趟至少 20 分鐘（約 10 站以上）。先坐著做；站立量測等流程熟悉後再做，並注意安全。

## 每趟的擺放方式

同一排、相鄰座位：

- **手機 A：支架**（主要量測方式）。螢幕朝自己，畫面保持在記錄頁。
- **手機 B：座椅上**平放在旁邊空位或自己腿上（不要拿起來）。
- **手機 C：手持**，正常滑手機的方式拿著，由觀察員拿。觀察員感覺到急煞或急加速時按「✋ 剛剛急煞了」。
- **硬體盒**：固定在同一排座椅骨架。

在首頁選好放置方式（支架、座椅上、手持）與座位，路線與車牌三支手機填一樣的。

## 流程

**上車前**
1. 三支手機打開網頁，填路線、車牌（看車頭或車身的車牌）、座位、放置方式。
2. 確認手機電量 > 50%，接上行動電源。
3. 硬體盒按 BOOT 開始記錄（LED 亮）。

**上車坐好後**
1. 三支手機都按「上車開始」，允許動作與定位權限（iPhone 會跳兩次）。
2. 手機 A 按「🔔 對時敲擊」，把手機 A 疊在硬體盒上，一起在椅背硬處輕敲一下。
3. 把各手機放到定位。手機 A、B 應在 2 秒內顯示「✅ 穩定量測中」。
4. 看一下記錄頁下方：取樣頻率約 60 Hz；車子起步幾次後，方向應變成「GPS 校準」。

**行駛中**
- **不要鎖屏、不要切到其他 App**（網頁在背景收不到感測資料）。
- 觀察員在紀錄表記下特殊狀況：急煞原因（前車、機車切入、紅燈）、靠站、轉彎、路面坑洞、車內擁擠程度。

**下車後**
1. 三支手機按「下車結束」，等摘要頁出現。
2. 按「分享全部檔案」，存到團隊共用雲端硬碟的 `raw/<日期>/` 資料夾。
3. 硬體盒按 BOOT 結束，SD 卡的 `box_XXXX.csv` 也放到同一個資料夾。
4. 在紀錄表填上這趟的檔名。

## 紀錄表欄位

日期、上車時間、下車時間、路線、方向、車牌、上下車站、座位（排、靠窗或走道、坐或站）、三支手機的型號與放法、硬體盒檔名、天氣、車內擁擠度（空、有座位、站滿）、特殊事件備註。
**不記錄司機姓名或任何可識別司機的資訊。**

## 每趟結束後的資料檢查

在電腦上跑：

```bash
cd analysis
uv run sunsunbus report data/ --out output/
uv run sunsunbus compare-box data/<手機A的檔名前綴> data/box_0001.csv --out output/
```

| 檢查 | 合格標準 | 不合格時 |
|---|---|---|
| 取樣頻率（`trips.csv` 的 `sample_rate_hz`） | ≥ 50 Hz | 記下手機型號與瀏覽器 |
| 穩定比例（`stable_ratio`） | 支架、座椅 ≥ 80% | 支架夾緊；看 `plots/*.png` 灰底在哪裡 |
| 前進方向（`orient_sources`） | 含 `gps` | GPS 訊號差（地下道），或起步太少 |
| 中斷（`summary.json` 的 `gaps`） | 無 | 提醒自己不要鎖屏 |
| 手機 A vs 硬體盒 `corr_a_long` | ≥ 0.9 | 先檢查對時（offset、敲擊有沒有被抓到） |

## 安全與禮貌

- 坐穩或抓好扶手再操作手機；支架不要擋走道或妨礙其他乘客。
- 不拍攝、不錄音、不打擾司機；這是量測車輛的運動，不是評比司機。
- 若司機或乘客詢問，簡單說明是在做公車平穩度的學生專題，資料匿名、不針對個人。

## 這些資料要回答的（給階段二報告）

- 各手機、各瀏覽器的實際取樣頻率與時間戳穩定度。
- 三種放法的雜訊差異（`distribution_by_placement.png`、與硬體盒的 RMSE）。
- 靜置偵測的門檻是否合適（支架被誤判為不穩定的比例；手持被誤判為穩定的比例）。
- 台北公車急煞的實際分布，預設門檻（加速 1.5、煞車 1.0 m/s²、加加速度下限 3.0 m/s³）是否需要調整。
- 人工標記與自動偵測的一致率。
- iPhone 加到主畫面後，螢幕常亮是否有效（**待實機驗證**）。
