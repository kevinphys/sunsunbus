# 原型二：遊戲版（小水滴澆站間）

依階段二 wireframe（第二版；設計稿只留在本機 `wireframe/`，不進 git）重新實作的七個畫面，網址是 `play.html`。
線上版：<https://kevinphys.github.io/sunsunbus/play.html?simulate=1&speed=8>（推到 main 後由 GitHub Actions 自動部署）。
感測、事件偵測、本機儲存、匯出都沿用研究用記錄器（`index.html`），遊戲版只多了「站間」與「果實」兩層。

```
web/play.html                 遊戲版入口
web/src/game/                 遊戲規則純函式（附單元測試，不碰 DOM）
  rules.ts                    參數型別；預設值在 shared/game.default.json
  segments.ts                 停靠偵測、站間切分、三級開花、TDX 站序解析
  ride.ts                     有效趟次、果實、探路果、路線水果
  demo.ts                     示範行程（7 站、6 個站間），模擬模式與測試共用
web/src/play/                 畫面
  main.ts                     ① 上車 ② 搭乘中 ③ 下車 review ④ 果籃 ⑤ 換乘車金 ⑥ 司機端 ⑦ 市府儀表板
  live.ts                     搭乘中：包住記錄器，即時切站間、偵測拿起手機、忘了按下車時自動結束
  ledger.ts                   果實帳本（localStorage，與搭乘資料分開）
web/scripts/game-check.ts     用實測 CSV 檢查站間切分與等級
```

## 試玩

```bash
cd web && npm run dev
# 電腦上：https://localhost:5173/play.html?simulate=1&speed=8   （示範行程，8 倍速，約 40 秒跑完）
# 手機上：https://<區網 IP>:5173/play.html?route=中山幹線&plate=KKA-1234&dir=0
```

- `route`、`plate`、`dir`（0 去程、1 返程）由支架的 NFC 貼紙或 QR 帶入。手機碰 NFC 貼紙會由作業系統打開網址，
  畫面顯示「從支架貼紙推測，你可能在搭」，按「對，是這班」（或點小水滴）就開始。iPhone 要求權限必須由點擊觸發，所以無法完全免點。
- 上車站由 GPS 自動偵測（首頁先抓一次顯示，開始記錄後以第一筆 GPS 為準），**不用先選下車站**。
- 下車時按「我下車了」，下車站取按下時 GPS 最近的站牌。
- `simulate=1` 播放示範行程，`speed=N` 快轉（只影響模擬）。示範行程在終點站停 40 秒，到站後按「我下車了」。
- 研究用記錄器首頁下方有「試玩遊戲版（原型二）」連結；兩邊共用同一個 IndexedDB，遊戲版的趟次也能在記錄器的「紀錄」裡匯出 CSV。

## 規則（實作版）

參數都在 `shared/game.default.json`，與感測演算法參數分開。

**站間切分**（`segments.ts`）

| 情況 | 停靠的判斷 |
|---|---|
| 有站牌資料 `web/public/stops/<路線>.json` | GPS 進入站牌 35 m 內算到站。範圍內有停車（< 1 m/s）就取停車的第一筆、最後一筆當到站、離站時間；過站不停取最接近站牌的那一刻。只往後找（站序遞增），一次最多往後 8 站 |
| 沒有站牌資料 | 速度 < 1 m/s 持續 5 秒算一次停靠，站名顯示「停靠 1、停靠 2…」。離上一次停靠不到 150 m 的併成同一次（站前排隊、走走停停）。紅燈也會被算成停靠，所以只是備援 |

事件依峰值時間歸屬：停靠前 → 到站的那一段（進站煞車）；停靠期間 → 不計分（開關門、上下車）；停靠後 → 離站的那一段（出站起步）。
上車處、下車處到第一個／最後一個停靠不足 150 m 的那一段略過。

**上車站與下車站**：有站牌資料時，第一筆 GPS 距最近站牌 100 m 內就認定為上車站，之後從這一站往後找（中途上車也對得上）。
按「我下車了」時，GPS 距最近站牌 150 m 內就是下車站，否則叫「下車處」。沒有站牌資料時不顯示上下車站名。

**三級開花**：每個事件依類型給點數（急煞、急加速、急轉彎各 1 點；**高加加速度 0 點**，見下方實測）。
任一事件超過嚴重門檻（急煞 2.5、急加速 2.2、急轉彎 2.5 m/s²）→ 乾土；否則 0 點盛開、≤ 2 點小花、更多乾土。
站間內 stable 取樣不到 60% → 「沒量到」，不給等級。

**果實**（`ride.ts`）：整趟 stable ≥ 50%、量到 ≥ 3 個站間、今天還沒滿 4 顆 → 1 顆（缺水任務 2 顆，不超過每日上限）。
量到的站間一半以上是乾土 → 探路果（價值相同）。20 顆換 15 元。

**結束**（`live.ts`）：主要靠乘客按「我下車了」。忘了按的保護：離所有站牌都超過 300 m 持續 60 秒（離開路線，需要站牌資料），
或手機不穩定超過 10 分鐘，就自動結束；這時只算開始離開路線／拿起手機之前到達的站，終點取其中最後一站（最後一個穩定量測的站）。
不穩定超過 2 秒畫面切成「小水滴在找支架」。

## 用第一趟實測校正（656，後排靠窗，手機平放座椅）

```bash
cd web && npx vite-node scripts/game-check.ts ../analysis/data/<檔名前綴>
```

沒有站牌資料，停靠推測切出 8 個站間（4.8 km）。

| 高加加速度點數 | 盛開 | 小花 | 乾土 |
|---|---|---|---|
| 0.25（初版） | 0 | 2 | 6 |
| **0（現行）** | **1** | **5** | **2** |

初版裡有一段 2.2 km 沒有任何急煞急加速，只因為 16 個高加加速度事件就變成乾土；分析（見 `analysis/`）顯示這趟的高加加速度事件 39/58 發生在等速行駛，
多半是後排路面顛簸，不該算在「這段開得順不順」。所以先設 0 點，事件仍保留在資料裡。這只是一趟、一個座位，前排與支架的實測後要再看一次。

另一個觀察：這趟幾乎每次進站都是 −1.8 至 −2.6 m/s² 的煞車，所以大部分站間是小花而不是盛開；嚴重門檻 2.5 m/s² 會讓最猛的兩段變乾土。

## 原型和正式版的差距

| 項目 | 原型 | 還需要 |
|---|---|---|
| 站牌資料 | 要手動放 TDX StopOfRoute JSON 到 `web/public/stops/<路線>.json`（`uv run sunsunbus fetch-tdx <路線>` 下載的 `<路線>_StopOfRoute.json` 改名即可） | 後端代理 TDX（金鑰不能放前端） |
| 「你可能在搭這班」 | 只有貼紙／QR 帶入，否則手動選路線 | 用 GPS 比對 TDX 即時車輛位置 |
| 果實帳本、兌換 | 只存在這支手機，兌換是示意 | 後端帳本、支付帳戶綁定 |
| 缺水任務 | 示意卡片，不會觸發 | 伺服器統計各路線 × 時段的樣本數 |
| 站間資料上傳 | 不上傳（文案照設計稿寫「匿名送給市府」） | 依 wireframe 的 `SegmentResult` 格式上傳，時間取整 15 分鐘 |
| ⑥ 司機端 | 用這支手機今天的旅程數字，否則示意數字 | LINE 官方帳號、業者排班對應 |
| ⑦ 市府儀表板 | 示意資料，或這支手機的資料（不套用 ≥ 10 趟門檻） | 伺服器彙整 |
| Python 分析 | 站間切分只有 TS 版 | 需要時移植到 `analysis/`，並加一致性測試 |
